Java · Featured project Built and tested Live-verified with OpenAI

Reconciliation Break Resolution Copilot

An independent Java/Spring demonstration of AI-assisted reconciliation. The model proposes a structured, evidence-cited recommendation; application policy and authorized reviewers control what happens next. The model never resolves a break on its own.

Java 21 · Spring Boot · Spring AI · PostgreSQL/pgvector · Kafka · Keycloak

How a request flows
1SubmitBreak and evidence over REST. The tenant comes only from the JWT. Evidence is de-duplicated by hash and chunked.
→
2RetrieveAsync investigation job. Hybrid search: pgvector plus keyword, fused with RRF. Evidence chunks are scanned for prompt injection.
→
3ProposeThe model returns a structured, cited root-cause proposal. Personal data is masked first. Optional route through ai-gateway (off by default).
→
4CheckCitations are verified. A policy gate picks manual review, L1 or L2 approval from confidence and variance.
→
5Approve & auditMaker and checker must differ. Every step goes into a hash-chained audit trail.
How it was tested
  • Automated checks: unit, integration (against a real PostgreSQL in containers) and UI suites. CI results are in the private repository and can be shown in a walkthrough.
  • Tenant isolation: PostgreSQL row-level security, with integration tests that also check isolation under virtual threads.
  • AI safeguards: citation verification, injection scanning, hybrid retrieval and the policy gate each have their own tests; the audit hash chain has an integration test.
  • Real provider, opt-in: tests against a real model provider are opt-in and excluded from CI. A live OpenAI run compared four investigation modes on a fixed question set; the multi-agent supervised mode did not meet its decision rule, so it stays off by default.

Not yet verified: the ai-gateway route is proven against a fake gateway only, not the real one. Code private; walkthrough on request.

Enterprise Knowledge Assistant (EKA)

Supporting proof of Python and RAG depth: a document ingestion and retrieval project exploring hybrid search, citations, refusal behavior, and tenant isolation. A Python core does the retrieval work behind a Java edge, showing how Python AI components can sit inside an enterprise Java architecture.

Python · FastAPI · PostgreSQL/pgvector · Embeddings · Java 21 edge · Angular

How a request flows
1AskThe Angular UI sends the question. The cited answer streams back over server-sent events.
→
2Java edgeSpring Cloud Gateway: OIDC sign-in, a short-lived internal token, rate limits, an audit record and a circuit breaker.
→
3RetrievePython FastAPI core. Hybrid search: dense (pgvector) plus full-text, fused with RRF. Tenant filter enforced by row-level security that fails closed.
→
4Refusal gateThe assistant answers only when the retrieved evidence is strong enough; otherwise it declines.
→
5CiteCitations are built on the server from the retrieved chunks, so the model cannot invent a source.
How it was tested
  • Automated checks: the Python core, the Java edge and the Angular UI each have their own unit and integration suites, with coverage measured.
  • Retrieval quality: a fixed question set scores the hybrid search (hit rate and rank), and the evaluation is part of CI.
  • Tenant isolation: row-level security is exercised by leakage tests against a real PostgreSQL.
  • Edge behaviour: identity, rate limiting, audit and resilience rules have their own edge tests.

Not yet verified: chat was checked with a fake model only, not a live one. AWS is Terraform-validated only and Bedrock is a stub.

Java · Featured project Built and tested

AI Gateway

A Java service between applications and language models. Every call is authenticated, checked for duplicates and sensitive data, held to a per-tenant token and cost budget, routed to a model, and recorded in a ledger.

Java · Spring Boot · LLM integration · PostgreSQL · Redis · Kafka

How a request flows
1AuthenticateRS256 JWT. The tenant comes only from the token; tenant headers are rejected, even with a valid token.
→
2AdmitRequired Idempotency-Key, rate limit and size limit. A retried call replays the stored result.
→
3GuardSensitive-data detection and masking, risk check, and a per-tenant token and cost budget reserved before the call.
→
4Route & callPick an eligible model (stub, OpenAI or Bedrock adapter) with fallback. A call that may have been sent is never retried.
→
5RecordOne ledger row per call with usage and cost. Events leave through a transactional outbox to Kafka (off by default).
How it was tested
  • Automated checks: extensive unit and integration suites. CI results are in the private repository and can be shown in a walkthrough.
  • Concurrency: integration tests send simultaneous requests for the same budget and the same idempotency key.
  • Sensitive data: classifier, routing and cache-key tests, plus an integration test for sensitivity routing.
  • Events: outbox tests cover transactional writes, the relay and a payload privacy check.

Not yet verified: Bedrock and AWS were not run live (fake endpoint and Terraform plan only). Code private; walkthrough on request.
